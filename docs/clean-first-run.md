# 新用户的环境列表保持为空

2026-11-02。旧启动入口 `open_env_window.py` 内嵌 `DEFAULT_ENVS`，普通启动会自动创建
`fb-008`、`fb-012`、`fb-020` 三个演示环境。检查的 v1.0.1 应用目录确实使用这一启动流程；
v1.0.2-local 和 v1.0.3-local 的产品快捷启动已绕过该分支，但应用中仍包含旧的自动初始化代码。
本次对三个应用目录的文件检查发现的是上述自动生成逻辑，没有发现散装个人环境定义、账号库
或浏览器数据库文件。这一检查不等同于对历史 EXE 和所有第三方压缩资源做完整安全审计。

现已删除演示定义与所有启动时的环境创建调用。普通启动、产品启动和复用入口均保持新用户
环境为空；仅主动新建/导入/API 写入时增加环境。原有 `--skip-envs` 参数继续兼容。不会按环境
名称删除已有数据，因为用户可能使用相同名称，旧演示环境也可能已被用户实际使用。

真实首次启动验收还发现配置目录的时序竞争：服务早于 Chromium 建立 Default 目录时，原先
依靠目录是否存在的路径判断会把命令通道与账号库放到上一级。现在启动器在启动服务前只建立
空的 `BrowserProfile/Default` 目录，不创建环境、账号或代理资料。

打包入口现执行只读 `installer/payload_policy.py`，在运行安装器编译器之前拒绝个人数据、
未批准的顶层文件/目录、个人 profile、浏览器数据库、开发凭据或演示自动创建逻辑。
安装文件验证也执行同一检查，发现问题直接失败，不通过删除用户数据来修复。

验证结果：

- 14 项启动与打包策略回归通过，覆盖两种入口、空 profile、复用、旧参数、已有环境/账号/代理
  摘要不变，以及合法使用 `fb-008` 名称的已有环境不被删除。
- 当前代码与独立运行时组成的 13,885 文件验收目录通过打包策略检查；未生成安装包。
- 私有 Windows 桌面、独立数据目录、普通用户 Medium token 下，真实产品启动 25 项检查全部通过。
  原生环境列表与管理 API 在首次启动均为空；显式创建验收环境后可打开，复用与重启后只保留
  该环境，不出现演示数据。还检查首次配置、侧栏开关、快捷入口复用、正常退出及用户桌面未切换。
- 早期验收用例存在文件安全标签与结果断言问题，已调整测试夹具和断言；仅最终全部通过的报告
  作为完成证据。并发初始化的重启断言使用服务完成时间，允许初始化进程先于新浏览器启动。

未更新安装版、未修改用户的现有环境、未提交或上传。已存在的 Setup EXE 字节不变，需在获准
重新打包后才能将本次修复交给安装包用户。汇总见 `.work/clean-first-run/completion.json`。
