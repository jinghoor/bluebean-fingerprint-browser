# DSH 并行运行加固记录

日期：2026-11-12。范围：开发版、发布源码与 v1.0.6 安装版。最终安装及运行检查已通过；详细范围见 [发布测试说明](RELEASE-1.0.6-TESTS.md)。

## 现象与证据

用户报告另一台电脑在独立 DSH 桌面端与蓝豆同时运行时，发消息后出现重连和
`agentPresets/list failed: Failed to fetch`；关闭独立桌面端后恢复。
目前没有那台电脑的故障日志，因此具体的跨进程冲突根因尚未确认。

本机检查表明，蓝豆的 DSH_HOME 与独立 DSH 的默认目录不同，Web 监听端口由
系统动态分配。官方桌面单实例锁只在 Electron 主进程中申请；蓝豆的 CLI
通过 Node 模式运行，不能仅凭可执行文件同名认定是单实例锁冲突。

另外，本机旧版 dsh-web.log 确实记录过 `spill-local` 创建临时文件时的
ENOENT：继承的 BlueBeanSetup-* 临时目录已被安装器清理。该问题有本机日志
证据，但不能据此认定它就是另一台电脑上所有并行运行故障的原因。

## 改动

- 沿用产品私有的稳定 Temp 目录，避免服务依赖安装器的临时文件生命周期。
- 统一 Web、SDK 和插件初始化子进程的环境构造；移除继承的 DSH Desktop
  通信变量、Electron 开关、Node 注入选项与其他实例的 bridge 地址/令牌。
- 从本产品的数据目录明确注入 DSH_HOME 和 bridge 配置，保留模型凭据、代理
  及权限模式等有意配置；不改系统环境变量，不复制或清理用户数据。
- Web 监听明确绑定 127.0.0.1，继续使用端口 0。
- 健康探测在认证页面之外，验证只读的 agentPresets/list RPC，避免首页正常
  而 Agent API 不可用时仍误报健康。原有连续失败与繁忙任务保护继续生效。
- 使用运行环境版本标记，下一次服务初始化时迁移旧启动环境。

## 验证

`installer/test_dsh_coexistence.py` 与 `installer/test_clean_startup.py`
共 22 项测试通过。覆盖隔离环境、私有 bridge 配置、启动参数、进程复用、
拒绝关闭非本产品进程、Agent API 健康检测以及空白新用户与已有用户数据保留。

`installer/verify_dsh_coexistence.py` 使用两个不同安装目录中的真实 DSH
可执行文件和全新的临时数据目录。它不启动可见窗口，也不使用真实模型凭据。
通过项目包括：

- 两个不同的动态端口；20 次并行 Agent 预设请求。
- 同时建立 WebSocket，并确认 ping/pong 正常。
- 两个后端均接收创建会话和发消息请求；随后 API 与 WebSocket 继续可用。
- 不同数据目录的认证 cookie 不互通。
- 退出其中一个测试后端，另一个仍能完成 10 次 API 请求。
- 故意注入其他桌面实例的 Electron/Node 变量和已删除的安装器临时目录，
  内嵌后端仍可启动与接收请求。

测试结束只关闭本次创建的测试进程；现有浏览器、环境、账号、Cookie、DSH
会话和凭据不变。结果报告不包含令牌或 cookie。

## 尚未验证

上述测试覆盖本机后端共存、认证、发消息接收及通信稳定性，未验证真实模型
回复，也没有覆盖用户故障电脑的完整独立 DSH 桌面应用。不能把本机测试通过
表述成原机冲突已经彻底消失。最终仍需在原机同时运行两款应用并发消息复验；
若继续断线，应定位实际退出码或接口响应，而不是要求用户永久关闭另一款应用。
